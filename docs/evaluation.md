## 运行仓库检查

在仓库根目录使用 Python 3.10 或更新版本运行，无需安装额外 Python 包：

```bash
python scripts/validate_repo.py
python -m unittest discover -s tests -v
```

如果本机的命令名是 `python3`，将上面的 `python` 换成 `python3`。

结构检查覆盖以下内容：

- 安装目录中的说明、参考示例、配置和图标齐全且非空。
- `SKILL.md` 的 frontmatter 分隔符、技能名称、目录对应关系及非空描述。
- Markdown 中简单相对文件链接的目标存在，且没有越出仓库；跳过代码围栏、外部 URL 和页内锚点。
- `openai.yaml` 中的图标引用可在技能目录内找到。
- 回归案例的字段类型、非空内容、唯一 ID、人工检查项与可选机械规则。

这是针对本仓库格式的轻量检查器，不是完整的 YAML / Markdown 解析器；它不会联网检查外部页面，也不会运行模型或自动判断“够不够阿里味”。单元测试会制造缺文件、错误元数据、坏引用和无效案例等情况，确认检查器能报错。

[GitHub Actions 工作流](../.github/workflows/validate.yml)会在提交、Pull Request 和手动运行时执行相同检查。每次运行的结果可在仓库的 Actions 页面查看。

## 执行行为回归

1. 在目标客户端安装当前要验证的技能版本，记录客户端、模型、日期与仓库提交。
2. 打开 [cases.json](../evals/cases.json)，每个案例使用独立的新对话，避免前一个案例的浓度、格式要求影响后一个。
3. 对 `should_trigger: true` 的案例，直接复制 `prompt`。需要显式选择技能的客户端可选择 `ali-style`，并记录这一操作。
4. 对 `should_trigger: false` 的案例，让技能保持可用，但不要手动选择技能、不要附上技能正文。检查普通周报和“阿里云”字样是否误触发风格。
5. 保存原始输出，逐条核对 `checks`。文字正确但没有执行客户端触发测试时，只记录输出表现，不声称已经验证自动触发。

不同客户端的技能发现与触发方式可能不同；案例中的 `should_trigger` 是期望行为，不是自动运行开关。

## 判断一次输出是否通过

| 检查方向 | 通过标准 | 常见失败 |
| --- | --- | --- |
| 数字与范围 | 数字、单位、基线、时间和环境限定一致 | 把百分点改成百分比，把压测效果写成生产收益 |
| 进度与贡献 | 已完成、进行中、计划中及个人职责准确 | 把参与写成主导，把尚未上线写成已闭环 |
| 因果与承诺 | 未知仍未知，建议仍是建议 | 凭同期变化认定因果，替用户承诺日期或指标 |
| 场景与语气 | 浓度符合要求，事故与延期直说影响 | 用黑话掩盖实际问题，给普通请求添加人格评判 |
| 格式与长度 | 遵守句数、篇幅和只给成稿的要求 | 一句话扩成长报告，额外输出选档过程 |
| 技能触发 | 按明确风格意图使用技能 | 只因出现周报或阿里云就使用阿里味 |

任何一项事实、进度、贡献或承诺被改写，都应判为未通过，即使文案很有风格。风格判断允许不同写法，不要求输出与某个固定句子完全一致。长度案例按输出正文字符数核对，标点计入，换行不计。

## 记录结果

复制下面的表格记录一次评估。建议保留原始输出，不只写“通过”。

| 案例 ID | 客户端 / 模型 | 技能提交 | 是否显式选技能 | 结果 | 输出及差异说明 |
| --- | --- | --- | --- | --- | --- |
| progress-01 | 待填写 | 待填写 | 是 / 否 | 通过 / 未通过 / 未执行 | 粘贴输出，并逐条核对 checks |

修改措辞规则时，至少重跑相关案例；修改触发描述时，加跑全部 `activation` 对照案例；修改目录或安装材料时，运行仓库检查并实际安装一次。针对明确变更验证即可，不需要每次文档勘误都重新评估全部模型。

## 保存输出并生成报告

[输出记录工具](../scripts/evaluate_responses.py)将实际输出与核对结论保存成 JSON，再生成 Markdown 报告。它不会连接模型、调用 API 或代替人工判断语义。

### 1. 生成空记录

全部案例：

```bash
python scripts/evaluate_responses.py template --output evaluation-responses.json
```

只准备本次相关的案例，可重复传入 `--case`：

```bash
python scripts/evaluate_responses.py template --case critique-01 --case technical-literals-01 --output evaluation-responses.json
```

已有文件默认不会覆盖；确实需要替换时追加 `--force`。两个命令选择一个执行即可。

### 2. 执行案例并填写原始结果

按前文的独立对话流程执行，把原始正文放进 `output`，不要为了通过字数或字面检查先修整答案。JSON 中的换行写为 `\n`，双引号写为 `\"`。模板的关键字段如下：

```json
{
  "schema_version": 1,
  "metadata": {
    "client": null,
    "model": null,
    "skill_revision": null,
    "date": null,
    "explicit_skill_selection": null
  },
  "responses": [
    {
      "case_id": "critique-01",
      "output": "",
      "manual_review": {
        "status": "pending",
        "notes": ""
      }
    }
  ]
}
```

`metadata` 填实际客户端、模型、完整技能提交和执行日期；不知道的项保留 `null`。`explicit_skill_selection` 为 `true`、`false` 或 `null`，表示这批案例是否显式选用技能；使用方式不同的案例分别存成记录文件。逐条核对案例的 `checks` 后，将人工状态改为 `pass` 或 `fail`，并在 `notes` 写明依据；尚未核对保留 `pending`。

空输出与缺少的案例都算未执行，即使误填 `pass` 也不计入通过数。示范文案和脚本测试用的合成文本不应冒充实际模型输出。

### 3. 生成报告

```bash
python scripts/evaluate_responses.py report --responses evaluation-responses.json --output evaluation-report.md
```

报告列出全部 20 个案例，保留原始请求、原始输出和检查项。未在本批记录中的案例显示 `NOT RUN`，因此只跑三个案例不会得到“20 个都通过”的报告。

| 字段或状态 | 含义 |
| --- | --- |
| `NOT RUN` | 没有非空原始输出，不算通过 |
| 机械 `PASS` / `FAIL` | 声明的字数或原样字符串规则通过 / 未通过 |
| `NO CHECKS` | 该案例未配置机械规则，仍需人工复核 |
| 人工 `PENDING` | 已有输出，但尚未填写人工结论 |
| 人工 `PASS` / `FAIL` | 记录者填写的复核结论，工具未独立验证 |

目前 4 个案例配置了机械检查。`max_chars` 统计 Unicode 码点，标点、空格、制表符计入，CR/LF 不计；组合字符和 emoji 可能占多个码点。`required_literals` 区分大小写、逐字匹配，不合并空白或转换全半角，仅用于输入明确要求保留的原文。字面通过不代表语义正确；字面失败需要看具体差异，不应直接扩展为模型整体质量结论。

退出码 `0` 表示文件已生成且没有已记录的失败，仍可能有未执行或待评案例；`1` 表示报告中有机械或人工失败；`2` 表示输入格式或文件读写有误。用于发布判断时，要同时查看覆盖数量和人工状态。

默认的两个本地记录文件已在 `.gitignore` 中排除。需要提交公开演练记录时，先确认内容适合公开，再用明确文件名保存到 `evals/`。已保存的[原始记录](../evals/sample-responses.json)与[生成报告](sample-report.md)可作格式参考。

## 新增案例

每个案例应有一个明确的失效风险，用合成或脱敏素材描述，检查项写成可以核对的事实。`id` 保持唯一，`category` 使用简短分类，`should_trigger` 必须为 JSON 布尔值。不要把真实同事、客户、公司内部信息或访问凭证写入案例。

新案例加入 [cases.json](../evals/cases.json) 后，运行结构检查，并在 Pull Request 中附一次实际输出及核对结果。格式见现有案例；完整贡献流程见 [CONTRIBUTING.md](../CONTRIBUTING.md)。

只有适合机械判断的明确要求才添加可选 `machine_checks`，例如 `{"max_chars": 90}` 或 `{"required_literals": ["Retry-After"]}`。长度必须是正整数，字面项必须是非空字符串；不支持的规则名会报错。不要用“出现闭环就通过”之类的关键词规则替代事实和风格评估。
